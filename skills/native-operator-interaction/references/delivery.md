# Delivery and handoff

## Respect the current client

Keep the chat answer self-contained: result, meaningful verification, limitation and the actual artifact location. A file on the agent's machine is not proof that the person received it. Distinguish created, opened, checked, attached and publicly available.

For Telegram or another attachment-based client, use the output directory and transport explicitly supplied by that client. Write a concise message and give the verified path in the required form. Do not invent an attachment protocol, an inaccessible file:// link or a public upload as a substitute. For a local editor, use its supported file link. For a native Canvas, use only an identifier returned by a verified creation tool and check access if possible.

Before delivery, check existence, nonzero content, readable permissions, actual opening and safe package contents. A browser preview of reconstructed HTML is weaker than opening the exact file; label the difference. Never include private source evidence merely because it helped create the explanation.

## Portability

The skill describes the output's semantics. The host supplies available tools, permitted file locations, language preferences and authority. Do not embed one machine's directory, IP, provider, token, browser service or workflow controller into portable instructions.

When the client cannot deliver HTML, provide a useful Markdown or text equivalent and say what interactivity is absent. Do not silently install a server or publish the report. Existing approved application renderers can be used without claiming that a local HTML file is a native collaborative document.

## Handoff

For an interrupted or transferred task, record only what the next actor needs:

- User objective, scope and completion criterion.
- Verified current state and dated/versioned evidence.
- Changes actually made and their ownership.
- Uncertainties, blockers and consequences.
- Existing permissions and actions still requiring a decision.
- Artifacts, next action, next owner and recovery/rollback for unfinished mutations.

Follow the existing project's canonical storage and task system. The skill does not create a new task database, activate a controller, select a goal by recent timestamp or keep a conversation alive indefinitely. Do not promote a source document or unverified inference to a permanent instruction.

Close after the requested output and necessary evidence are delivered, or identify the real blocker. A next step is included only if work actually remains. Store reusable findings only when permitted by the host and within the designated memory/project scope.
